The problem underneath the problem

A payment doesn't happen in one step. It's a handoff across several services, aggregator to switch to issuing bank, and the questions people actually care about ("did this complete end to end?", "where exactly are we losing transactions?") live across multiple log lines, not inside any single one. Standard logging tools are great at showing you an event. They're bad at showing you a transaction. And this gap matters a lot at NBBL, where faster visibility into exactly where something stalled directly shortens how long dispute resolution takes.

Who actually needs this

The core audience is anyone on the product or ops side keeping an eye on transaction health day to day. But honestly, the more interesting audience is everyone else, leadership, partner facing teams, people who need to understand what's going on without an analyst translating it for them first.

What I actually built

I started with the data model, not the dashboard, which turned out to be the right call. I modeled a transaction as a single correlated chain of messages tied together by one reference ID, and made that same ID double as a replay safe record identifier. The tricky part was handling transactions that fail partway through. I settled on a "null after drop" approach: once a transaction fails at some stage, everything after that stage is explicitly marked null rather than just missing, which is exactly the shape you need for a proper funnel or drop off analysis.

Since I didn't have access to a live feed to build against, I generated a realistic synthetic dataset instead, about a thousand log records forming a few hundred transactions, with a deliberate mix of success, failure, and latency patterns covering every path a transaction could take. That let me build and actually test the whole thing before any real data ever touched it.

The output is two things that stay live and update in place: an interactive dashboard (funnel, success rate, where transactions leak, latency tails, error codes, all clickable straight down to the underlying records with CSV export) and a companion guide written in plain language, so someone without an analytics background can look at any chart and understand what it's telling them.

I looked at just using a BI tool like Power BI here too. Honestly it's fine for the dash-boarding part, but it doesn't help with the actual hard part, which was correlating raw events into a coherent transaction model and writing a guide that explains it in plain language. I'd have had to do that manually either way. Claude Cowork handled the modeling, the synthetic data, the pipeline, and the live dashboard together, without needing an engineer, and kept all of it versioned and regenerable.

The tradeoff I knowingly accepted: I gave up the polish and governance you'd get from an enterprise BI rollout in exchange for speed. A new question becomes a new panel the same session I ask for it, instead of going through a request queue to a dash-boarding team.

Scope, in and out

In for v1: the transaction grain data model, the synthetic dataset and generator, the core dashboard panels, the paired interpretation guide, and the standing update loop.

Out for now: hooking it up to a live pipeline, alerting thresholds, and breakdowns by individual bank or aggregator.

The goal for this round was proving the model and the interaction pattern, chart to drill down to guide, before spending time wiring it into anything live.

How it actually runs

Every request starts as "visualize X." It checks whether a chart or dataset for that already exists. If not, it models the new slice of the transaction grain, flags any assumption that wasn't dictated by spec, regenerates the dataset if needed, runs it through the pipeline, updates the dashboard in place, and appends a new entry to the guide. Nothing spawns a new file. Everything grows in the same two living artifacts.

Where this goes next: connecting it to a real live feed, adding alerting thresholds on leak patterns, and eventually breaking results down by individual bank or aggregator, which maps directly onto reconciliation work I already do.

What surprised me most: almost all the value came from getting the data model right, not the charts. Once the null-after-drop logic clicked, the funnel basically fell into place. The bigger lesson: build the process model first — the interface is only ever as good as what's underneath it.
